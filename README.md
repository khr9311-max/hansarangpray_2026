# 사랑의교회 청년부 한반도이웃사랑선교국 2026 짝기도 매칭

QR로 신청을 받아 짝을 지어주고, 빔프로젝터 화면에서 추첨하듯 조를 공개하는 현장용 웹앱입니다.

- **운영 사이트**: https://hansarangpray-2026.vercel.app
- **프레임워크**: Next.js 15 (App Router · Server Actions)
- **운영 저장소**: Supabase PostgreSQL
- **스타일 / 호스팅**: Tailwind CSS v4 / Vercel
- **전환 전 데이터**: [짝기도 데이터 시트](https://docs.google.com/spreadsheets/d/1AagqNZCvtBWlNtiUHiH6HFU1Rxy3NYYyK5ge-p3schs/edit)
- **시트 보관용 스크립트**: [짝기도 Apps Script](https://script.google.com/home/projects/1mkO6GSsf2OM-YdjUnCe1L46p2ekcPL8ceKIeiFpG-k_hh0Y80hJvkimG/edit)

앱 서버가 서버 전용 키로 Supabase 저장 함수를 호출합니다. 공개 화면의 변경 확인에는 행사 버전 번호만 전달합니다. 운영 전환 전 시트는 당시 명단을 보관하며, 최신 명단은 관리자 화면에서 CSV로 받을 수 있습니다.

## 화면

| 경로 | 용도 |
| --- | --- |
| `/` | QR로 진입하는 참가자 입력 폼 |
| `/admin` | 비밀번호로 보호하는 접수 현황 · 조별 이름과 주차별 기도 체크 · 추첨 시작 · 추첨 기록 복원 · 수정 · CSV · 현재 기록 숨기기 |
| `/admin/history` | 관리자 전용. 저장된 조 편성, 숨긴 기록, 이전 시트에서 이름·팀·조·기도제목 확인 |
| `/display` | 빔프로젝터 송출 화면. 이름만 표시 |
| `/me/[참가자id]` | 본인 조의 기도제목·주차별 기도 현황을 보고 본인의 1~4주차를 체크하는 개인 링크 |
| `/edit/[참가자id]` | 본인 수정 권한 또는 관리자 권한으로 신청 정보 수정 |

다른 기기의 변경은 화면이 약 5초마다 행사 버전 번호를 확인해 자동 반영합니다. 서버는 2초간 조회를 공유합니다. 화면으로 복귀했을 때도 갱신합니다.

### 기도제목과 개인 링크

웹앱에서는 관리자 화면과 본인 조의 개인 링크에서만 기도제목을 보여 줍니다. 모두가 보는 `/display`에는 이름만 전달하며, 페이지 소스에도 기도제목이나 실제 참가자 ID를 넣지 않습니다. 저장소 시트에 접근할 수 있는 운영자는 전체 데이터를 볼 수 있으므로 시트는 필요한 운영자에게만 공유합니다.

신청 후 받은 `/me/[id]` 링크를 같은 브라우저에 45일간 기억합니다. 같은 브라우저로 다시 접속하면 새 폼 대신 개인 링크를 표시하며, 다른 사람의 신청을 위한 **새로 신청하기** 버튼도 제공합니다. 매칭 전에는 대기 안내를 표시하다가 조 편성이 완료되면 자동으로 자기 조를 보여 줍니다.

개인 링크는 추측하기 어려운 UUID를 이용하며 조회에 로그인을 요구하지 않습니다. 전달받은 사람도 내용을 볼 수 있으므로 본인에게만 전달합니다. 기도 체크 변경에는 신청한 브라우저의 본인 권한이 필요합니다. 기존 데이터 이전에서는 UUID를 유지하므로 이전 개인 링크도 계속 사용할 수 있습니다.

### 1~4주차 기도 체크

각 주차의 체크는 본인이 **우리 조를 위해 기도했다**고 기록하는 자기 보고입니다. 개인 링크에서 **1주차·2주차·3주차·4주차**를 각각 체크하거나 해제할 수 있습니다. 본인의 체크만 변경할 수 있으며, 같은 조원들의 주차별 현황은 읽기 전용으로 함께 표시합니다. 관리자는 `/admin`에서 조별 이름과 각 참가자의 주차별 상태를 확인합니다. 체크하지 않은 항목은 **미체크**로 표시하며, 실제 기도 여부를 판정하지 않습니다. 조가 다시 편성되거나 지난 회차를 복원해도 체크 기록은 참가자를 따라 유지됩니다. 자동 알림 메시지는 보내지 않습니다.

새 기기에서 사용하거나 본인 권한이 없는 이전 버전 참가자는 관리자가 명단의 **본인용 기도 체크 링크**를 본인에게만 전달합니다. 해당 링크를 사용할 기기에서 열면 본인 권한을 설정하고 개인 화면으로 이동합니다. 링크는 발급 후 45일간 유효하며, 기기에 설정되는 권한도 링크 만료 시각을 넘지 않습니다. 본인용 링크는 다른 사람에게 공유하지 않습니다.

### 송출과 추가 참가자

신청 화면과 송출 화면에는 **휴대폰 기도제목 입력 완료 후 창을 닫지 말아주세요!** 안내가 표시됩니다. 신청 QR은 대기·추첨·결과 단계에서 계속 유지합니다. QR은 요청 주소로 서버에서 생성하며 `NEXT_PUBLIC_SITE_URL`로 주소를 고정할 수도 있습니다.

송출 화면의 단계는 다음과 같습니다.

1. **대기**: 신청 이름표와 QR을 보여 줍니다.
2. **준비**: 관리자가 `/admin`에서 조 인원과 방식을 선택하고 **추첨 시작**을 누르면 조 편성을 저장하고 8초 뒤 공개하도록 예약합니다.
3. **추첨**: 예약 시각에 3.2초 동안 이름표를 섞는 연출을 진행합니다.
4. **결과**: 저장된 조별 카드를 공개합니다.

**추첨 시작** 한 번으로 조 편성과 공개 예약을 처리하며 `/display`는 자동으로 진행합니다. 8초의 준비 시간 동안 각 화면이 예약 시각을 받아 같은 시각에 3.2초 연출을 시작합니다. 추첨 시각을 시트에 함께 저장하며, 네트워크 지연이나 화면 복귀 시에는 저장된 공개 상태로 갱신합니다. 저장된 현재 조를 다시 보여 주려면 `/admin`의 **현재 조 다시 공개**를 사용합니다.

매칭 뒤에 QR로 신청한 사람은 대기 인원으로 표시됩니다. 관리자가 **추가 참여자 반영**을 누르면 미배정자를 인원이 적은 기존 조부터 배정합니다. 기존 조원·조 번호·조 수를 유지하며 처음 정한 인원을 초과할 수 있습니다. **현재 조 다시 공개**는 저장된 조를 다시 공개하므로 추가 신청자는 먼저 **추가 참여자 반영**으로 배정합니다.

### 추첨 기록과 복원

관리자 화면의 추첨 기록에는 현재 회차와 지난 회차가 날짜별로 남습니다. 새로 **추첨 시작**을 실행해도 이전 회차의 조 편성은 기록에 보관됩니다. 원하는 회차를 복원하면 저장된 조를 활성화하고 8초 준비와 3.2초 추첨 연출 뒤 자동 공개합니다. 복원은 해당 회차의 조 편성을 사용하며 새 조를 생성하지 않습니다.

**이 회차 보기**에서 이름, 팀, 조 번호, 기도제목을 확인할 수 있습니다. 이전 회차의 조 번호는 해당 회차의 배정을 표시하며, 참가 정보는 현재 저장된 내용을 표시합니다.

과거 회차를 복원하면 그 회차에 배정되지 않은 현재 참가자가 대기 인원으로 더 표시될 수 있습니다. **추가 참여자 반영**으로 기존 조에 합류시킬 수 있으며, 같은 회차에 이미 추가 배정한 조원은 나중에 그 회차를 다시 복원해도 유지됩니다.

### 행사 종료와 이력 관리

관리자 페이지에서 `삭제`를 입력하고 **현재 기록 숨기기**를 누르면 송출 화면과 현재 명단이 비워지고, 기존 참가자의 개인 링크로는 조와 기도제목을 볼 수 없게 됩니다. 신청 폼에서 새 행사를 시작할 수 있습니다. 관리자 메뉴의 **이력 관리**에는 숨긴 시점의 이름, 팀, 기도제목, 회차별 조 배정과 주차별 기도 체크가 보관됩니다. 조에 배정되기 전인 참가자도 이력에 남습니다. 명단에서 한 명을 숨긴 경우에도 그 참가자를 이력에서 확인할 수 있습니다.

**이력 관리 → 이전 시트 기록**에서 Supabase 전환 전 시트에 남아 있는 회차와 조원 정보를 조회합니다. 이전 시트의 읽기 전용 상태를 유지하므로 조회할 때 현재 명단이나 송출 화면은 바뀌지 않습니다.

## 입력과 매칭

| 항목 | 형태 |
| --- | --- |
| 이름 | 20자 이내 |
| 팀 | 영등포쪽방촌팀 · 단비팀 · 통일선교팀 · 전도팀 · 운영팀 · 국장 · 교역자 |
| 기도제목 | 500자 이내 |

직접 나누기를 선택하면 **기도제목은 매칭된 조 안에서 직접 나눌게요.**를 저장합니다. 개인 링크·관리자 화면·CSV에도 이 의사가 표시됩니다. 팀 목록은 `NEXT_PUBLIC_TEAMS`로 변경합니다.

[`src/lib/matching.ts`](src/lib/matching.ts)는 2~10인 조와 두 매칭 방식을 제공합니다.

- **팀 섞기 (`team`)**: 인원이 많은 팀부터 번갈아 배치하고 같은 팀의 겹침이 적은 조를 고릅니다. 40회 시도해 가장 적게 겹친 결과를 사용합니다.
- **완전 랜덤 (`random`)**: 팀 조건 없이 Fisher–Yates 셔플로 배치합니다.

정원을 채운 뒤 남는 사람은 기존 조에 한 명씩 더 배치하거나 잔여 조로 묶습니다. 전체 인원이 정원보다 적으면 한 조로 묶습니다.

## 구글시트 저장소 보관 및 복구

전환 전에는 위 데이터 시트와 독립형 Apps Script 프로젝트를 연결했습니다. 시트 저장소를 별도 검증 환경에서 사용할 때는 `PRAYER_STORAGE_BACKEND=sheets`를 지정합니다. 아래 최초 설정은 별도 새 시트 저장소를 만들 때 사용합니다.

### 1. 새 저장소의 최초 설정

1. 새 데이터 시트를 준비하고 Apps Script에서 새 프로젝트를 만듭니다. 시트의 **확장 프로그램 → Apps Script**로 연결된 프로젝트를 만들어도 됩니다.
2. [`google-apps-script/Code.gs`](google-apps-script/Code.gs)를 기본 코드에 붙여 넣습니다.
3. 프로젝트 설정에서 **편집기에 appsscript.json 매니페스트 파일 표시**를 켜고 [`google-apps-script/appsscript.json`](google-apps-script/appsscript.json)을 적용합니다.
4. 스크립트 속성 `SPREADSHEET_ID`에 실제 사용할 시트 ID를 설정합니다. 현재 저장소의 값은 `1AagqNZCvtBWlNtiUHiH6HFU1Rxy3NYYyK5ge-p3schs`입니다. 시트에 연결된 프로젝트에서 실행하면 `setup()`도 연결된 시트 ID를 기록합니다.
5. 편집기에서 `setup()`을 실행하고 소유자 계정으로 필요한 시트·외부 요청 권한을 승인합니다. 기존 데이터를 덮어쓰지 않고 필요한 탭·헤더·초기 행사 상태를 확인합니다.
6. 프로젝트 설정의 스크립트 속성에서 자동 생성된 `SHEETS_API_SECRET`을 확인해 서버 환경변수에 저장합니다. 직접 지정할 때는 추측하기 어려운 **32자 이상**의 값을 사용합니다.

매니페스트는 Sheets v4 서비스를 선언합니다. 기본 Apps Script Cloud 프로젝트에서는 Sheets API가 함께 활성화됩니다. 별도의 표준 Google Cloud 프로젝트에 연결했다면 그 프로젝트에서도 Google Sheets API를 활성화해야 합니다.

시트는 다음 탭을 사용합니다. 열 제목과 식별자 열을 변경하지 않습니다.

| 탭 | 내용 |
| --- | --- |
| `participants` | 참가자 이름·팀·기도제목·등록 시각·수정 버전 |
| `match_rounds` | 조 편성 회차와 활성 여부 |
| `match_groups` | 회차별 조 번호 |
| `match_members` | 조와 참가자의 연결·표시 순서 |
| `match_control` | 행사 버전·공개 시각. 기본 숨김 |
| `participant_submissions` | 신청 재시도 중복 방지 ID. 기본 숨김 |
| `prayer_checkins` | 참가자별 `week_1`~`week_4` 기도 체크. 기본 숨김 |
| `prayer_archive` | 관리자 이력의 참가자 정보와 회차별 조 배정. 기본 숨김 |

`prayer_checkins`는 `participant_id`와 4개의 참·거짓 열로 저장하며 시트에서도 기본 체크박스로 표시합니다. 체크하지 않은 참가자는 모두 미체크로 표시합니다. 기존 저장소에 이 탭이 없으면 `setupPrayerCheckins()`를 실행합니다. 새 저장소는 `setup()`으로 초기화합니다. 기존 저장소의 `prayer_archive` 탭은 새 Apps Script 배포에서 처음 기록을 숨길 때 생성됩니다.

### 2. 웹 앱 배포

Apps Script에서 **배포 → 새 배포 → 웹 앱**을 선택합니다.

- **다음 사용자 인증 정보로 실행**: 나(배포 소유자)
- **액세스 권한**: 모든 사용자
- 배포 후 나온 `https://script.google.com/macros/s/.../exec` 주소를 서버 환경변수에 저장

웹 앱 접근을 허용해도 구글시트 자체를 공개할 필요는 없습니다. 데이터 읽기·쓰기는 서버 비밀키를 확인한 POST 요청만 처리합니다. 배포 주소의 GET 응답은 서비스 상태만 보여 줍니다. 코드를 수정한 뒤에는 **배포 관리 → 수정 → 새 버전**으로 반영합니다.

### 3. 서버 환경변수와 실행

`.env.example`을 `.env.local`로 복사해 설정합니다. 저장소 주소와 비밀키에 `NEXT_PUBLIC_`를 붙이지 않습니다.


신청·수정·조 편성·추가 배정·공개·삭제는 Apps Script의 `LockService` 잠금으로 순서대로 처리합니다. 여러 탭의 변경은 Google Sheets의 원자적 `batchUpdate` 한 번으로 저장합니다. 오래된 화면의 변경은 행사 버전으로 거절하고, 신청 수정도 수정 버전으로 덮어쓰기를 막습니다.

**행사 중 데이터 수정은 웹앱 관리자 화면에서 진행합니다.** Apps Script 잠금은 사람이 시트에서 직접 편집하는 작업까지 조정하지 않습니다. 시트에서 직접 값을 바꾸면 행사 버전·조 연결과 맞지 않을 수 있습니다. 숨김 탭은 화면 정리용이며 접근 권한을 대신하지 않습니다.

### 호출량과 동시 접수

Sheets API의 기본 쓰기 한도는 **사용자·프로젝트당 분당 60회**, 프로젝트 전체는 분당 300회입니다. 여러 변경을 묶은 `batchUpdate`도 한 번의 쓰기로 계산합니다. 이 앱은 배포 소유자로 실행하므로 참가자마다 별도 한도를 받는 구조가 아닙니다. 실제 프로젝트의 한도는 Google Cloud 설정에서 확인합니다. [Google Sheets API 사용량 제한](https://developers.google.com/workspace/sheets/api/limits)

QR 신규 신청은 웹 서버 인스턴스마다 잠시 모아 최대 50건을 함께 보냅니다. Apps Script가 잠금을 잡고 신규 참가자, 신청 키, 행사 버전을 한 번의 `batchUpdate`로 저장합니다. 서버는 각 신청 키에 대응하는 참가자 ID를 확인한 뒤 완료 화면을 표시합니다. 일시적인 연결 오류나 잠금 경합은 같은 신청 키로 자동 재시도합니다. 이미 저장된 키는 기존 참가자 ID를 반환합니다. [Apps Script 할당량과 제한](https://developers.google.com/apps-script/guides/services/quotas)

시트 저장소를 사용하는 환경은 새 Apps Script 버전을 기존 웹 앱 배포에 먼저 적용한 후 Next.js를 배포합니다.

## Supabase에서 시트로 내보내기

이전 도구는 현재 참가자·회차·조·조원·행사 상태·중복 신청 방지 기록을 옮깁니다. 숨긴 이력은 원본 저장소에 보관됩니다. UUID, 개인 링크, 수정 버전, 등록·공개 시각을 유지합니다. 기도 체크 기능이 없던 기존 데이터에서 `prayer_checkins`가 누락된 경우에는 빈 체크 기록으로 처리합니다. Supabase의 API 최대 행 수는 1000 이상이어야 합니다.

Node.js 22 이상에서 로컬 `.env.local`에 `SUPABASE_URL`(기존 `NEXT_PUBLIC_SUPABASE_URL`도 허용)과 `SUPABASE_SERVICE_ROLE_KEY`를 설정합니다.

1. Apps Script를 설정하고 웹 앱 배포 주소·비밀키를 로컬 환경변수에 넣습니다.
2. 우선 `npm run migrate:sheets -- --export-only`를 실행합니다. 기본 실행도 같은 확인 동작으로, 로컬 백업과 테이블별 행 수만 만들고 구글시트에는 쓰지 않습니다.
3. 전환 시간 동안 기존 사이트 접수와 모든 관리자 변경을 중단합니다. 새 배포가 확인될 때까지 중단 상태를 유지합니다.
4. `npm run migrate:sheets -- --apply`를 실행합니다. 비어 있는 대상 시트에만 가져오며, 기존 데이터가 있으면 덮어쓰지 않습니다.
5. 이전 뒤 모든 행을 다시 읽어 원본과 비교한 결과를 확인합니다. 참가자 개인 링크와 관리자 명단·조 편성도 확인합니다.
6. 아래 배포 절차로 운영 사이트를 전환하고 확인한 뒤 접수를 재개합니다. 확인이 끝나기 전에는 Supabase 데이터를 삭제하지 않습니다.

백업은 Git에서 제외한 `.tmp.driveupload/migration/`에 시각별 JSON으로 저장합니다. 개인정보가 포함되므로 공개 업로드하거나 저장소에 커밋하지 않습니다. 실행 로그에는 비밀키와 개인별 데이터를 출력하지 않습니다.

스크립트는 읽기 전후·가져오기 직전·직후에 Supabase 행사 버전을 확인합니다. 버전 검사는 서로 다른 시점의 데이터를 섞어 옮기는 일을 감지하지만, 기존 운영 사이트의 접수를 직접 중단해 주지는 않습니다. 시트에 데이터를 가져온 뒤 원본 변경이 감지되면 운영 전환을 멈추고 두 저장소를 확인해야 합니다.

## 시트에서 Supabase로 이전

Supabase 런타임과 이전 마이그레이션을 적용하고, 대상의 쓰기 차단을 유지한 채 작업합니다. 시트와 Supabase 서버 연결 정보를 `.env.local`에 설정합니다. 스크립트는 전환 직전 양쪽의 현재 행사 데이터를 Git에서 제외된 `.tmp.driveupload/migration/`에 보관하고, 참가자 UUID와 편성·기도 체크·중복 신청 키를 포함한 행을 검증합니다. 숨긴 이력은 각 원본 저장소에 보관됩니다.

1. `node scripts/migrate-from-sheets.mjs --export-only`로 시트에서 내보내기가 되는지 확인합니다.
2. `node scripts/migrate-from-sheets.mjs --freeze-source`로 시트 쓰기를 중단합니다. 최종 이전 동안 운영진도 시트를 직접 수정하지 않습니다.
3. `node scripts/migrate-from-sheets.mjs --apply`로 옮깁니다. 기존 데이터가 든 대상이라면 스크립트가 표시한 기존 Supabase 버전을 확인해 `--replace-target <버전>`을 함께 지정합니다.
4. `node scripts/migrate-from-sheets.mjs --verify`로 두 저장소를 비교합니다. 전환할 앱의 관리자 명단, 송출 화면, 개인 링크를 확인합니다.
5. [`supabase/unfreeze-for-sheets.sql`](supabase/unfreeze-for-sheets.sql)로 Supabase 쓰기를 열고, Supabase에 연결한 배포를 운영 도메인에 연결합니다. 이전 Apps Script는 읽기 전용으로 유지합니다.

## 배포와 현장 운영

Vercel에서 `PRAYER_STORAGE_BACKEND=supabase`, `SUPABASE_URL`, 서버 전용 `SUPABASE_SECRET_KEY`, `ADMIN_PASSWORD`, `NEXT_PUBLIC_TEAMS`를 설정합니다. 기존 Supabase URL과 `SUPABASE_SERVICE_ROLE_KEY` 환경변수도 지원합니다. `NEXT_PUBLIC_SITE_URL`은 주소를 고정할 때만 추가합니다. 기존 관리자 쿠키·수정 링크의 유효성을 유지하려면 전환 중 `ADMIN_PASSWORD`를 그대로 사용합니다.

이력 관리 기능을 배포할 때는 [Supabase 이력 마이그레이션](supabase/migrations/20261120132606_archive_prayer_records.sql)을 먼저 적용한 뒤 웹 앱을 배포합니다. 전환 전 회차를 조회하려면 서버 전용 `GOOGLE_SHEETS_WEB_APP_URL`과 `GOOGLE_SHEETS_API_SECRET`에 이전 Apps Script 연결 정보를 설정합니다.

배포 전에는 `npm test`, `npm run build`, `node --test scripts/migrate-to-sheets.test.mjs`를 실행합니다. Apps Script 테스트는 `node --test google-apps-script/backend.test.cjs`로 실행합니다. 테스트 명단으로 신청 → 본인 수정 → 추첨 시작과 자동 공개 → 늦은 참가자 추가 → 지난 회차 복원 → 개인 링크의 기도 체크 → CSV → 현재 기록 숨기기와 이력 조회를 확인합니다.

1. `/display`를 빔프로젝터에서 전체화면으로 엽니다.
2. 참가자가 QR로 신청하고 개인 링크를 유지합니다.
3. 진행 시점에 관리자가 `/admin`에서 조 인원과 방식을 고르고 **추첨 시작**을 누릅니다. 조 편성을 저장하고 8초 준비 후 3.2초 추첨 연출과 결과 공개를 자동 진행합니다.
4. 늦은 참가자는 **추가 참여자 반영**으로 배정합니다. 같은 조를 다시 보여 줄 때는 **현재 조 다시 공개**, 지난 조로 돌아갈 때는 추첨 기록의 복원을 사용합니다.
5. 참가자는 개인 링크에서 자기 조의 기도제목과 주차별 현황을 확인하고, 우리 조를 위해 기도한 주차에 본인이 체크합니다. 관리자는 `/admin`에서 조별 체크 현황을 확인합니다. 새 기기에서는 관리자에게 **본인용 기도 체크 링크**를 받아 그 기기에서 엽니다.
6. 행사 종료 뒤 필요하면 **CSV 내려받기**로 현재 명단을 저장합니다. `삭제`를 입력해 **현재 기록 숨기기**를 실행하고, **이력 관리**에서 방금 숨긴 내용을 확인합니다.

`node tests/fixture-server.cjs`는 운영 데이터에 연결하지 않는 로컬 검증 서버(3030/3031)를 엽니다. 로그인 암호 `fixture-only-password`는 검증 전용입니다. `tests/event-transaction.sql`과 `tests/supabase-runtime.sql`은 별도 PostgreSQL 검증 환경에서 실행하고 마지막에 롤백합니다.
